Introduction

This series explains, step by step, how this website is built, so that you can build a similar one for yourself. This first post is the map: it describes the pieces, how they fit together and what happens when a page is opened. The following posts take one piece at a time and build it from scratch.

You do not need to be a web developer to follow the series. You need to be comfortable editing text files, to know the basics of Git (clone, commit, push), and to be curious about HTML, CSS and a little JavaScript. Every post shows complete, working code.

A static website

The most important design choice is that the website is static. There is no server-side program (no PHP, no Python, no Node.js running on a server) and no database. The website is just a folder of files: HTML pages, CSS stylesheets, JavaScript scripts and images. A web server sends these files to the browser exactly as they are stored.

Everything that looks dynamic is done by the browser, with a few lines of JavaScript: inserting the navigation bar into every page, listing the blog posts, building the search index, filtering the theses, switching to the dark theme.

Why static

  • Free hosting. GitHub Pages publishes static websites at no cost.
  • Nothing to maintain. There is no server to update, no database to back up, no plugin with security holes.
  • Fast. Files are served as they are, from a content delivery network, and the browser caches them.
  • Versioned. The whole website is a Git repository: every change is recorded, can be reviewed and can be undone.
  • Portable. The same folder works on any web server, or on your laptop.

What you give up

  • No server-side logic: forms cannot be processed by the website itself (this website uses e-mail links and an external Google Form instead).
  • No user accounts: a page cannot be shown only to logged-in users. A later post shows how to protect a page with encryption instead.
  • Repetition must be avoided by hand, which is what the “shared parts” mechanism is for.

Pages as templates

The pages in the root are templates: they define the layout and contain empty containers. The actual text lives in separate files, which the template loads when the page is opened. Two kinds of content are loaded this way:

  • shared parts (navigation bar, side columns, footer), identical on every page, from common/;
  • page content, different for each address: the text of the home page, a blog post, a project post, the list of theses.

Each piece of information exists in exactly one place. The navigation bar is written once and appears on eleven pages; a blog post is written once and appears in the list of posts, on its own page, in the tags and in the search results.

External libraries are few and loaded from public CDNs: jQuery (to write shorter JavaScript), Font Awesome (icons), Fuse.js (search, loaded only when used) and the Inter font. There is no build step and no package manager: what is in the repository is exactly what the browser receives.

What happens when a page opens

Let us follow the browser when you open the address of this post, /projectPost?project=website&post=overview:

  1. GitHub Pages receives /projectPost, finds no file with that exact name, and serves projectPost.html. The part after ? (the query) is ignored by the server and left to the page.
  2. The first lines of the <head> run immediately: they apply the dark theme if you chose it on a previous visit, and remove a trailing .html from the address bar if you came from an old link.
  3. The browser loads the stylesheets and the scripts listed in the <head>.
  4. The body is parsed: the layout and the empty containers are created. Right after them, loadPartial() fills the containers with the navigation bar, the left column and the footer, taken from memory if you have already visited another page.
  5. A script of the page reads project=website and post=overview from the query, downloads posts/projects/websitePosts/overview.html and inserts it into the central column.
  6. The scripts included in the post run: tableContent.js builds the table of contents in the left column from the headings of the post, and the comments are loaded.

All of this takes a fraction of a second, and only the last two steps involve this specific post: everything else is shared with the rest of the website.

Common tasks

To give an idea of how the pieces are used in practice, this is what the most frequent changes involve:

TaskWhat to do
Publish a blog postadd posts/blog/<name>.html and its name to posts/blog/index.json
Add a post to a projectadd the file to posts/projects/<project>Posts/ and a line to the project timeline
Add a thesisadd a card to thesis-card.html
Change the menuedit common/navBar.html
Change a colouredit one variable at the top of assets/css/modern.css
Add a pagecopy an existing page, keep the containers, change the central column, add it to the menu

In all cases the list of posts, the tags and the search update by themselves. Changes are made on a separate branch, tested on the local computer with a small server that behaves like GitHub Pages, and only then published: the next post explains this workflow.
