Introduction

Sometimes a page should not be part of the public navigation: a guide meant only for my students, or a project I do not want to show to everyone. A static website has no login, but there are still two useful options, with very different levels of protection.

Unlisted pages

An unlisted page is a normal page that is simply not linked from the menu or from other pages, and that asks search engines not to index it. Whoever has the link can open it; everyone else will not stumble upon it. The guides for my students are published this way under /howTo/. 

<meta name="robots" content="noindex, nofollow">

These pages live in subfolders (howTo/writeThesis/index.html), so their relative links would point to the wrong place. A <base> element makes all relative links start from the root of the website again: 

<base href="/">

Unlisted is not private: the files are in a public repository, and the link can be passed on. It is the right choice for content that is harmless if found, but not meant for everyone.

Password-protected pages

For real protection the content must not be readable at all without the password. On a static website the only way is encryption: the repository contains only encrypted files, and the browser decrypts them after the visitor types the password. The password is never stored anywhere, and the encrypted files are useless without it.

Encrypting the files

The readable pages and images are kept in a folder excluded from Git (private/, listed in .gitignore), so they never reach the public repository. A Python script encrypts them with AES-256-GCM, using a key derived from the password with PBKDF2 (600 000 iterations, which makes guessing passwords slow), and writes the encrypted .enc files that are published: 

key = PBKDF2HMAC(algorithm=hashes.SHA256(), length=32,
                 salt=salt, iterations=600_000).derive(password)
aes = AESGCM(key)
for page in pages:
    iv = os.urandom(12)
    write(page + ".enc", iv + aes.encrypt(iv, read(page), None))

A small public file stores the salt, the number of iterations and an encrypted test string, used to check whether a password is right.

Decrypting in the browser

When the protected page is opened, it shows a password box. The browser derives the key with the same parameters, using the built-in Web Crypto API, and tries to decrypt the test string. If that fails, the password is wrong; otherwise the page is decrypted and displayed: 

const base = await crypto.subtle.importKey("raw", encode(password), "PBKDF2", false, ["deriveKey"]);
const key  = await crypto.subtle.deriveKey(
  { name: "PBKDF2", hash: "SHA-256", salt, iterations },
  base, { name: "AES-GCM", length: 256 }, true, ["decrypt"]);
const html = await crypto.subtle.decrypt({ name: "AES-GCM", iv }, key, data);

The key is kept in the session storage, so the visitor types the password once and can then read all the posts of the project until the tab is closed. Images are encrypted too: they are downloaded, decrypted and shown from memory (as blob addresses), so the original image files are never published.

Search and protected content

The site search must not reveal protected content, so protected pages are not part of the public index. Only in a tab where the password has already been entered, the search decrypts those pages too and adds them to the results; the decrypted index stays in that tab.

Limits

  • The protection is as strong as the password: choose a long one.
  • Everyone who knows the password can read the content and pass it on.
  • Every change to a protected page means running the encryption script again.
