Introduction

Sometimes a page should not be part of the public navigation: a guide meant only for my students, or a project I do not want to show to everyone. A static website has no login, but there are two useful options, with very different levels of protection: unlisted pages and encrypted pages. This post builds both.

Unlisted pages

An unlisted page is a normal page that is not linked from the menu or from other pages, and that asks search engines not to index it. Whoever has the link can open it; everyone else will not stumble upon it. The guides for my students are published this way, under /howTo/: 

howTo/
├── index.html                  /howTo/                     list of guides
├── prepareThesisGit/
│   └── index.html              /howTo/prepareThesisGit/
└── writeThesis/
    └── index.html              /howTo/writeThesis/

Not indexed

<meta name="robots" content="noindex, nofollow">

Search engines that respect this line do not show the page in their results, and do not follow its links. The pages are also left out of the site search.

Links from a subfolder

All the shared parts and scripts use links relative to the root (./common/navBar.html, assets/css/modern.css). From a page inside howTo/writeThesis/ those links would point to howTo/writeThesis/common/..., which does not exist. One line in the <head> makes all relative links start from the root again: 

<base href="/">

The price is that links to sections of the same page must then be written in full (/howTo/writeThesis/#introduction instead of #introduction), because #introduction alone would now point to the home page.

What unlisted means

Unlisted is not private: the files are in a public repository, and anyone can pass the link on. It is the right choice for content that is harmless if found, but not meant for everyone.

Password-protected pages

For real protection the content must be unreadable without the password, even for someone browsing the repository. On a static website the only way is encryption: the repository contains only encrypted files, and the browser decrypts them after the visitor types the password. The password itself is never stored or published.

The ingredients

  • AES-256-GCM, a standard symmetric cipher. GCM also detects tampering: decrypting with a wrong key fails instead of producing garbage, which is how a wrong password is recognised.
  • PBKDF2 with SHA-256, to turn the password into a 256-bit key. It is deliberately slow (600 000 iterations), so that trying millions of passwords is impractical.
  • A random salt, public, so that the same password gives a different key on different websites.
  • A random IV (initialisation vector) for each file, stored at its start.

Encrypting: a Python script

The readable pages and images are kept in private/, a folder listed in .gitignore, so they never reach the public repository. A script encrypts them with the cryptography package and writes the .enc files that are published: 

import base64, getpass, json, os
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.hazmat.primitives.kdf.pbkdf2 import PBKDF2HMAC

password = getpass.getpass("Password: ").encode()
salt = os.urandom(16)
key = PBKDF2HMAC(algorithm=hashes.SHA256(), length=32,
                 salt=salt, iterations=600_000).derive(password)
aes = AESGCM(key)

def seal(data):
    iv = os.urandom(12)
    return iv + aes.encrypt(iv, data, None)        # IV + ciphertext + tag

for name in os.listdir("private/project"):
    data = open(f"private/project/{name}", "rb").read()
    open(f"posts/projects/project/{name}.enc", "wb").write(seal(data))

# public parameters + an encrypted test string to check the password
json.dump({"iterations": 600_000,
           "salt": base64.b64encode(salt).decode(),
           "check": base64.b64encode(seal(b"ok")).decode()},
          open("assets/data/lock.json", "w"))

The password is typed in the terminal (getpass does not show it), so it never appears in a file or in the shell history.

Decrypting in the browser

Checking the password

The protected page first shows a password box. When the visitor submits it, the browser derives the key with the same parameters, using the built-in Web Crypto API, and tries to decrypt the test string. If decryption fails, the password is wrong: 

async function unlock(password) {
  const meta = await (await fetch("assets/data/lock.json")).json();
  const base = await crypto.subtle.importKey(
    "raw", new TextEncoder().encode(password), "PBKDF2", false, ["deriveKey"]);
  const key = await crypto.subtle.deriveKey(
    { name: "PBKDF2", hash: "SHA-256", salt: b64(meta.salt), iterations: meta.iterations },
    base, { name: "AES-GCM", length: 256 }, true, ["decrypt"]);
  await decrypt(key, b64(meta.check));     // throws if the password is wrong
  return key;
}

function decrypt(key, bytes) {
  return crypto.subtle.decrypt(
    { name: "AES-GCM", iv: bytes.slice(0, 12) }, key, bytes.slice(12));
}

Web Crypto is available only on secure pages (https:// or localhost), which GitHub Pages provides.

Showing pages and images

After a successful unlock, the page downloads the encrypted post, decrypts it and inserts it as usual. Images are encrypted too: before inserting the post, their addresses are moved to a data- attribute, so that the browser does not request the (missing) originals; each image is then downloaded encrypted, decrypted, and shown from memory with a blob address: 

const plain = await decrypt(key, await getBytes(path + ".enc"));
img.src = URL.createObjectURL(new Blob([plain], { type: "image/webp" }));

Remembering the key for the visit

Deriving the key takes a moment by design, and typing the password on every post would be annoying. The derived key is therefore kept in the session storage: the visitor types the password once and can read all the posts of the project until the tab is closed.

Search and limits

Protected content and the site search

The public search index must not contain protected text, otherwise the search would reveal it. Protected pages are left out of the index. In a tab where the password has already been entered, however, the search decrypts them and adds them to a separate index that stays in that tab, so that they can be searched like everything else.

Limits

  • The protection is as strong as the password: choose a long one, not used elsewhere.
  • Everyone who knows the password can read the content and pass it on.
  • Each change to a protected page means running the encryption script again.

Try it yourself

  1. Create an unlisted page in a subfolder, with noindex and <base>.
  2. Encrypt a short HTML file with the script and decrypt it in the browser console with unlock and decrypt.
  3. Try a wrong password and check that decryption fails.
