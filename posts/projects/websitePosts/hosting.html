Introduction

In this post we put a first page online. We create the repository, write a minimal page, publish it with GitHub Pages, and set up a local server to test changes before publishing them. At the end you will have a public address, such as https://<username>.github.io, and a workflow to update it safely.

What GitHub Pages is

GitHub Pages is a free service of GitHub that takes the files of a repository and serves them as a website. There is no server to configure: you push files to the repository, and GitHub publishes them, usually within a minute. It is designed exactly for static websites like this one.

A few limits are worth knowing from the start:

  • the repository of a free account must be public: anyone can read your files on GitHub (keep this in mind for anything you would not publish);
  • the published website should stay below 1 GB, and a single file below 100 MB;
  • there is a soft limit on traffic (about 100 GB per month), far above what a personal website needs;
  • only static files are served: no PHP, no databases, no server-side code.

What you need

  • a GitHub account (free);
  • Git installed on your computer (git --version in a terminal should print a version number);
  • a text editor (any: VS Code, Sublime Text, even Notepad);
  • Python 3, for the local server (python3 --version).

Step 1: create the repository

A personal website lives in a repository with a special name: <username>.github.io, where <username> is your GitHub account name, in lowercase. This website is in the repository fghio.github.io and is published at https://fghio.github.io.

  1. On GitHub, click New repository.
  2. Name it <username>.github.io, exactly.
  3. Make it public.
  4. Tick Add a README file, so that the repository is not empty, and create it.

Then clone it on your computer: 

git clone https://github.com/<username>/<username>.github.io.git
cd <username>.github.io
Any other repository name also works, but the website is then published in a subfolder: a repository called notes appears at https://<username>.github.io/notes/. For a personal website, the special name is simpler.

Step 2: a first page

The home page of a website is always called index.html. Create it in the root of the repository with this content: 

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Jane Doe</title>
</head>
<body>
  <h1>Jane Doe</h1>
  <p>Aerospace engineer. This website is under construction.</p>
</body>
</html>

The two <meta> lines are important: the first makes accented characters display correctly, the second makes the page readable on phones (without it, phones show a zoomed-out desktop page).

Commit and push: 

git add index.html
git commit -m "First page"
git push

Step 3: publish

  1. On GitHub, open the repository and go to Settings → Pages.
  2. Under Build and deployment, choose Source: Deploy from a branch.
  3. Choose the branch main and the folder / (root), then Save.
  4. Open the Actions tab: a workflow called pages build and deployment runs. When it turns green, the website is online.

Open https://<username>.github.io: you should see your page. From now on, every push to main publishes a new version, and the history of the website is the history of the repository.

If it does not work

  • 404 page. Wait a couple of minutes and reload; check that the file is called index.html (lowercase) and is in the root, not in a subfolder.
  • Old version. The browser may show a cached copy: reload with Ctrl+Shift+R (Cmd+Shift+R on a Mac).
  • Works locally, broken online. GitHub Pages runs on Linux, where file names are case-sensitive: Photo.jpg and photo.jpg are different files. Use lowercase names, or check that links match exactly.

Addresses without .html

GitHub Pages also serves a file when the address omits the .html extension: /curriculum shows curriculum.html. In the same way, a folder with an index.html inside is reachable by its name: howTo/index.html is /howTo/.

This makes addresses shorter and nicer to share (“go to fghio.github.io/curriculum”), so all internal links of this website are written without the extension: 

<a href="./curriculum">Curriculum</a>        <!-- instead of curriculum.html -->

Old links with the extension keep working. To keep the address bar tidy also for visitors arriving from an old link, each page starts with a tiny script that removes the extension without reloading the page: 

<script>
  (function () {
    var p = location.pathname;                      // e.g. /curriculum.html
    if (/\.html$/.test(p))
      history.replaceState(null, "",
        p.replace(/(^|\/)index\.html$/, "$1")        // /index.html -> /
         .replace(/\.html$/, "")                      // /curriculum.html -> /curriculum
        + location.search + location.hash);         // keep ?query and #anchor
  })();
</script>

history.replaceState only changes what the address bar shows; the page is not reloaded and the browser's back button behaves normally.

Step 4: a local test server

Publishing every change to see whether it works would be slow and would expose half-finished pages to visitors. Changes should be tested on your computer first.

Double-clicking an HTML file opens it with an address that starts with file://. Simple pages work, but this website loads its shared parts and posts with JavaScript, and browsers block these requests for files opened from the disk. You need a local web server.

Python includes one: python3 -m http.server serves the current folder at http://localhost:8000. It has two differences from GitHub Pages that matter here: it does not understand addresses without .html, and it lists the files of folders without an index.html. The script below, saved as tools/serve.py, fixes both and also disables caching, so that every change is visible at the next reload: 

#!/usr/bin/env python3
"""Local server that behaves like GitHub Pages."""
import http.server
import os
import sys

ROOT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))


class Handler(http.server.SimpleHTTPRequestHandler):
    def __init__(self, *args, **kwargs):
        super().__init__(*args, directory=ROOT, **kwargs)

    def translate_path(self, path):
        fs_path = super().translate_path(path)
        # /curriculum -> curriculum.html, as on GitHub Pages
        if not os.path.exists(fs_path) and os.path.isfile(fs_path + ".html"):
            return fs_path + ".html"
        return fs_path

    def list_directory(self, path):
        # GitHub Pages never lists the files of a folder
        self.send_error(404, "File not found")
        return None

    def end_headers(self):
        # no cache: every change is visible at the next reload
        self.send_header("Cache-Control", "no-cache")
        super().end_headers()


if __name__ == "__main__":
    port = int(sys.argv[1]) if len(sys.argv) > 1 else 8000
    print(f"http://localhost:{port}  (Ctrl+C to stop)")
    http.server.ThreadingHTTPServer(("127.0.0.1", port), Handler).serve_forever()

Run it from the root of the repository and open http://localhost:8000: 

python3 tools/serve.py        # http://localhost:8000
python3 tools/serve.py 8080   # on another port

The server listens only on 127.0.0.1, so it is reachable from your computer and not from the rest of the network. Stop it with Ctrl+C.

Step 5: a safe workflow

The main branch is what visitors see. To avoid publishing something broken, the work happens on a second branch, here called development: 

git switch -c development       # once: create the branch and move to it

Then, every time:

  1. work on development and test with the local server;
  2. commit as often as you like (nothing is published);
  3. when everything works, bring the changes to main and push.
git switch development
# ... edit, test on http://localhost:8000 ...
git commit -am "New post on dark mode"

git switch main
git merge development
git push                         # published
git switch development           # back to work

Pushing development too (git push -u origin development) keeps a backup of the work in progress on GitHub without publishing it: GitHub Pages only looks at main.

If a change goes online and turns out to be wrong, git revert on main undoes it with a new commit, and the previous version is back online a minute later.

Files that should not be published

Since the repository is public, anything committed is visible to everyone, including in the history of old commits. A .gitignore file in the root lists files that Git must ignore: system files, editor settings, and anything private. 

# system and editor files
.DS_Store
Thumbs.db
.vscode/
__pycache__/

# private material, never published
private/

Optional: your own domain

If you own a domain (for example janedoe.com), GitHub Pages can serve the website on it: enter the domain in Settings → Pages → Custom domain, and at your domain registrar add the DNS records that GitHub indicates. GitHub then provides a free HTTPS certificate. This website keeps the github.io address, which needs no configuration and no yearly fee.

Try it yourself

  1. Create the repository and publish the first page.
  2. Add a second page, about.html, and a link to it from index.html written as href="./about".
  3. Check both pages with the local server, then publish and check them online.
  4. Open /about.html online and confirm that it shows the same page.
