Why tex2html

Because of the kind of work I do, it is much easier for me to produce text in LaTeX than in HTML. That is great for writing scientific documents, but not so great for quickly creating articles to add to this website. The problem gets worse when the post is long and complex, or contains equations, figures, tables or pieces of code, as this one does. Alas, Markdown is not convenient for me either, since I am not used to it.

So, to make writing posts for the projects and blog sections easier, I decided to build a LaTeX-to-HTML text converter in Python, and I called it "tex2html".

Two notes. First: a tool like this probably already exists, but I found it faster to write one from scratch than to make an existing online tool work (or even just adapt my writing to it). Second: this post has a bit of an "Inception" effect. In fact, the HTML of this very post comes straight out of the tool presented here. After all, what better way to test it?!

From LaTeX to plain HTML

Let's start from the beginning. I will not explain here what a LaTeX document is, or how to write one. There are plenty of examples for that, and less experienced readers are invited to watch one of these.

Here I only refer to the main features that a LaTeX document contains. The document can be split into two big parts: the preamble and the body. The preamble contains at least the document class, the packages to load and the definition of any macros. The body (the more interesting part for us) can contain: text, images, tables, bulleted or numbered lists, code snippets, and so on.

Clearly, the HTML we generate as the output of the conversion must not depend on the document class. On the contrary, the layout of the HTML depends on the container it is placed in, which in turn depends on the structure of the website. The packages loaded in the LaTeX document do not matter for the conversion either. So, to keep the LaTeX-to-HTML conversion general and make it easy to produce output usable on the website, we try to limit the use of macros (especially those related to equations).

What is left to convert, then, is the content of the file "text.tex" in the body of the LaTeX document; and, keeping in mind the "inception" mentioned above, this very article was built from that same "text.tex" file.

Let's start from a simple case: the file only contains plain text (like many of these paragraphs).

We write a Python script that reads text.tex and writes the output to output.html. The Python function must therefore: 1) read each line of the input tex file; 2) put <p> in front of it; 3) close it with </p>. Any CSS style can be added to the paragraph declaration (<p>), as long as it is compatible with the style of the website where the output will be placed. An example is given below:

Lines may also contain bold text, italic text, or combinations of the two. For this reason it is convenient to write a function that: 1) parses each line; 2) understands which style is active; 3) replaces the LaTeX command with its HTML counterpart; and finally 4) closes the style (bold, italic, ...) when it is no longer in use. With this simple trick we can handle generic text, without figures, tables, lists, equations, ... exactly like this one. While parsing the lines we may also find a hyperlink (as happened a little earlier in this post). The same helper function can detect that a link is present in the text and turn it into a link that HTML understands, as indeed happened above.

Equations and lists

The next step is handling formulas. Of course, the text may contain mathematical formulas or equations written using: a) dollar signs as delimiters, or b) a wrapper for the equation environment. Since the output must be easy to render on the web, the second option is preferable for complex equations. For the simple version (dollar delimiters) it is enough to add one more dollar sign at the beginning and at the end of the equation. For complex formulas, the code must be able to interpret a formula such as

$$ \nabla \cdot \mathbf{u} = 0 \tag{1}$$

producing an output like the one you are seeing on screen. To interpret the equation correctly, it is enough to check whether the LaTeX lines contain "begin equation". If they do, the HTML math environment is switched on until the reader meets "end equation". Everything inside the (LaTeX) equation environment can then be converted (to HTML), giving the result shown in Equation 1.

Of course, if the text contains at least one equation, the line that loads MathJax must also be added at the end of the generated HTML. MathJax is what renders mathematical formulas on the web.

Going into the details of the implementation, tex2html is Python code organised in classes. For the math environment, the Math class is imported and used to

  • switch on the equation environment in HTML;
  • write the equations in a MathJax-compatible format;
  • close the environment when the equation is over.

Particular care is also needed for equation numbering, so that equations can be referenced precisely in the text.

The previous paragraph shows another feature! Numbered (or bulleted) lists often appear in texts, and the tool must be able to handle them. It works much like the equation environment: tex2html loads the class that handles bulleted and numbered lists; the file is read line by line; the corresponding HTML environment is switched on when a list appears in the text; the content is split into items; the environment is closed when the list is closed in the LaTeX file.

Combining environments (math and lists, for example) is a natural next step. Indeed, bulleted or numbered lists can contain equations. The tool handles these situations by cross-checking when multiple environments are switched on and off, keeping in mind that equation can typically be nested inside itemize or enumerate, while the opposite is not true.

Figures and tables

The next step is the figure environment. Figures can be included in LaTeX text with includegraphics. The figure environment is switched on and off as shown above for equation and itemize. The figure has its caption and its label, both easy to handle. In LaTeX it is common to use "centering" (preferable to "begin center") to center the image. In this tool, "centering" is deliberately skipped. Image sizing is much harder to handle, and it often depends on the HTML environment the image is placed in. For this reason, sizing is left to the interested reader (and developer). Here is an example anyway, keeping in mind that the path to the image may differ between the LaTeX and the HTML environment.

Mind one detail. On the web everything is sequential, so there is no need to reposition figures in the HTML text (there is no page layout to do). That is why, in LaTeX, no placement option was given next to the figure environment (e.g. [!ht]). Such options are not supported by this conversion tool anyway.

As before, the table environment and the tabular sub-environment are recognised, switched on for the HTML construction, and closed (both in LaTeX and in HTML) according to begin and end. Of course, cells may contain mathematical equations (typically inline, i.e. delimited by dollar signs). So each line (or the content of each cell of the table) can be passed through the filter that finds and converts inline equations. The equations are converted to HTML, giving the result shown in the example above. The table has its caption, and is therefore reproduced correctly (and in a general way), depending on the CSS settings of the website it is placed in.

Personally, since I want a consistent style for tables, I add an HTML style at the end of the conversion, only once (even if the text contains more than one table), if the table environment was used at least once.

Code blocks

Last step: algorithms. Not easy at all, and the explanation will be a bit involved. Let's start from an example (even though other examples have already been shown above):

In LaTeX, algorithms sit inside the verbatim environment. So, as before, we can detect when it starts and ends with "begin" and "end" verbatim. Everything inside can be turned into lines of code to show in an HTML post. Of course, this does not explain the nice look of the code in this post (inspired by Lei Mao, who uses my same template). First of all, tex2html must store the lines inside the verbatim environment. These lines must be counted and split into their main parts, without removing the indentation, which for some languages is essential as well as pleasant to look at. The code is split according to its main parts, which are coloured to make it easier to read, based on the CSS style. For the splitting and conversion there is a very handy library: "pygments". This way we can take it for granted that the content of the code is handled correctly.

In HTML, the environment has two extra features (useless in LaTeX): 1) fold/unfold the code; 2) copy to the clipboard. Here is a quick explanation of how they work.

Each code block produced in HTML has a number attached (a random number drawn at generation time), and therefore an identifier. The fold/unfold and copy scripts use it to know which code block they refer to. Both icons are clickable. In one case (fold/unfold), a click changes the state of that code block only, so its content is shown or hidden. At the same time, the arrow changes direction to show that the content can be folded or unfolded. In the other case (copy), the content of the algorithm is copied to the clipboard, whether it is currently shown or not. To show that the copy worked, the icon in the top right corner turns into a check mark.

This structure is built for every algorithm in the text, each with its own identifier. The scripts, instead, are written to the output only once, at the end of the conversion of the LaTeX document, and only if the document contains at least one algorithm.

Wrapping up

This concludes the (very superficial) explanation of how the tex2html converter works. Interested readers can clone the repository, fork it, propose suggestions, additions, changes... or tweak the code however they like!

Once again, bringing you a needlessly complicated tool for a fairly simple problem. This time, though, with a touch of inception!
